## 0. 一句话

**把一段小说或剧本，变成一支 30～60 秒的剧情短片；关键节点由人把关，中间全部可回退、可追溯。**

V1 的核心不是"一次端到端生成"，而是一条**可控的创作流程**。这句话决定了后面所有设计：
每个阶段都能单独重做、每次生成都留版本、每次花钱前都有一道门。

```
文本导入 → 故事线/范围 → Story Bible → 分镜 → 关键帧 → 单镜头视频 → 合成与导出
              ↑              ↑           ↑         ↑                      ↑
           审核①           审核②       审核③     审核④                 审核⑥
                                                        审核⑤（锚点门，卡住"批量生成"这个花钱点）
```

审核节点由 `checkpoint_service.REVIEW_NODES` 定义，共 **6 个**（代码事实，不是宣传口径）：
`storyline_review` · `scope_review` · `bible_review` · `storyboard_review` · `anchor_review` · `quality_gate`。
其中对外常说的"三道门"指**真正卡住推进/花钱**的三处：范围、视觉锚点、代表性镜头。

## 1. 实现内容（做了什么）

### 1.1 技术栈与规模

| 层 | 技术 | 规模（行） |
|---|---|---|
| 后端 | FastAPI + SQLite + LangGraph + 异步任务 | 40 文件 / **15,403** |
| 前端 | 原生 JS（无框架）+ 单文件 CSS | 6 文件 / 5,515；CSS 1,854；HTML 239 |
| 工具与测试 | Python / Node（Playwright） | 97 文件 / **27,737**（测试 `test_*` 54 文件 / 15,413；工具 43 文件 / 12,324） |
| 文档 | Markdown 为主 | 18 份，交付文档 190 KB |

提交总数 **97**（2026-06-19 首提交 → 2026-10-01），分支 `feat/v1-media-pipeline`。

### 1.2 功能面

**主流水线**（`backend/services/` 20 个模块）
- 长文本分级：≤1500 字直调；1500–1 万字分块+事件+候选故事线；1 万–10 万字**章节树**逐章分块+按章圈范围；>10 万字**明确拒绝**。
- 改编：确定性 mock 规划器产出 2–3 个方案 → Story Bible → 分镜草案（带原文引用）。
- 镜头：关键帧（首/尾帧）、参考图、单镜头视频、**版本快照**（`shot_versions` 不可变，草稿独立存 `shot_drafts`）。
- 合成：FFmpeg 统一 1280×720 / 24fps / yuv420p / libx264；可选**保留原声**（P6-E）、背景音混音、字幕烧录（P6-D）。

**审核门**（真实关卡，不是标签。代码里共 6 个审核节点，见 `checkpoint_service.REVIEW_NODES`）
| 节点 | 卡住什么 |
|---|---|
| `storyline_review` / `scope_review` | 未选故事线 / 未确认改编范围，不能进改编 |
| `bible_review` | 未确认 Story Bible，不能生成分镜 |
| `storyboard_review` | 未确认分镜，不能进镜头制作 |
| `anchor_review` | 未确认视觉锚点，`assert_batch_generation_allowed` 抛 `ANCHOR_REVIEW_PENDING`，**批量生成视频被真正拦住** |
| `quality_gate` | 成片前的质量关卡 |

**可回退 / 可追溯**
- 上游重做只失效必要下游，**历史版本与旧视频保留**。
- "回滚"只改 `current_version_id` 指针，不复制资产、不重跑、不花钱。
- 每次真实调用记录 Provider、模型、版本、参数、次数、血缘（`assets` / `media_transfers` / `video_tasks`）。

**护栏**（与功能同等重要）
- 付费闸门在 `video_provider.generate_video_asset` **分发环**：开 HTTP 前判「授权 → 每项目次数 → 预算」，覆盖**全部** provider；被拦抛 `BLOCKED_BEFORE_CALL`，**原样上抛**不被兜底吞掉。
- 单价按 provider 取，未登记取最贵档。
- 密钥与 Data URL **不入库、不进 `job_events`、不出现在界面**。

### 1.3 视频 Provider 现状（2026-10-01）

| Provider | t2v | i2v | keyframes | reference | 状态 |
|---|---|---|---|---|---|
| **dashscope**（默认） | ✅验 | ✅验 | ✅验 | ✅验 | 四模式全覆盖，**均已真实验收** |
| minimax | ✅验 | ✅验 | ✅验 | ✗ 接口无此参数 | 兜底 |
| ~~ark~~ | — | — | — | — | **已退役**（余额门槛，且重复覆盖） |

## 3. 实现与测试（怎么保证不塌）

### 3.1 一条命令跑完全部：无费用回归

```
.venv\Scripts\python.exe tools\run_no_cost_regression.py
```

**61 项检查**，分四层，重的在后：

| 层 | 项数 | 内容 |
|---|---|---|
| 静态 | 7 | `compileall backend+tools` + 6 个前端 JS 语法检查 |
| Node 单元 | 7 | 视图模型、provider 解析、任务观察器、live 2shot 驱动 |
| Python 服务/契约 | 32 | 能力矩阵、版本、改编（短/中/长）、资产上传、任务中心、合成 A–E、锚点门、检索、读预算、锁容忍、付费闸门、**驱动器自检**、清理、远程任务退役 |
| 浏览器 | 15 | 工作台、关键帧、范围草稿、锚点 UI、P6C–E 真实预览、UI 状态、P8A/B、V1 QA/易用/演示、建项目守卫 |

**当前基线：61/61 · 581 pass / 0 fail / 1 skip**（最近两轮同口径全绿，逐项 counts 0 项不一致）。

### 3.2 三条被反复验证的原则

1. **用例缺陷 vs 产品缺陷，先分开再动手。** 一批失败里多数是测试自己的问题（异步竞态、陈旧读数、错误兜底端点）。把这类当产品缺陷去改业务代码，是最贵的错误。
2. **跳过不许静默。** skip 会让覆盖悄悄缩水，而缩水不报错。每一个 skip 都要能说出为什么。
3. **兜底路径不许静默。** 主路径超时改走另一条路，必须打印可见日志，否则与真实缺陷无法区分。

### 3.3 夹具与隔离

- 每轮独立 `run-<ts>/` 目录，**从不删目录**（可回查）。
- 每个 check 独立数据目录（`VISIONCRAFT_DATA_DIR`）与空闲端口，避免顺序耦合导致"失败点漂移"。
- 驱动器两个自检：**单实例锁**（防两个全量并行，结论全作废）+ **绝不把陌生后端当自己的**（防把用例跑在别人的数据目录上）。

## 4. 检验（凭什么说它是对的）

### 4.1 断言条数**必须**对得上，不只看全绿

`checks 61/61` 只说明没有失败项；**断言条数变了必须能解释到具体某一条**。
相对上一版：58 项/555 → 59 项/563 → **61 项/581**，每次增量都指得出来（章节勾选草稿 9 条 + P5-B-2 第一层 9 条）。**条数变化必须可归因。**

### 4.2 零漂移证明

新增一轮与基线轮做**逐项 counts 对比**。**0 项不一致** = 最强形式的零漂移（比"总断言数相同"强得多，能抓出"这项多 1 这条少 1"的抵消）。
最近一次：`run-20261001-203025` vs `run-20261001-185023` → **0 项不一致**。

### 4.3 证伪检验：证明用例有分辨力

新写的用例，必须做一次**"临时关掉修复 → 用例要在预期位置失败 → 还原 → 核对文件指纹"**。
否则它可能只是空壳（永远绿的用例 = 没有用例）。

- 勾选草稿修复：关掉修复 → 用例恰在"重绘后未保存的勾选丢了"处红 → 还原核对 sha256。
- 读路径容错：往临时项目**注入脏值**打**运行中的**服务 → 期望 200 且字段退化为 `[]`（不是 500）→ 清理干净。证明是**代码在挡**，不是数据恰好干净。

### 4.4 判据必须能证伪

- **`status: completed` 不等于验收通过。** 首尾帧验收要抽「起/中/末」帧与两张输入横排比对，且尾帧要与首帧构图差异够大（正面↔背影、亮场↔暗场）——**差异不够大的判据证明不了"收束"**。
- **耗时异常不作为回归判据。** 逐项耗时整体均匀放大 3.8× 而 counts 与断言完全一致 ⇒ 那是**环境因素**，不是产品回归。判据永远是**计数与断言**。
- **`elapsed` 不是跨轮可比指标**，两轮总耗时相同可以是巧合。

### 4.5 真钱验收（护栏 ≠ 验证）

**护栏只保证"万一要花先拦得住"，不保证"画面对不对"。** 已付费验收：

| 批次 | 内容 | 结果 | 实付 |
|---|---|---|---|
| 2026-08 | 三家 T2V | 通过 | — |
| 2026-08 | 三家 I2V 同一首帧 | 通过 | — |
| 2026-08-31 | 5 镜真实成片 | 通过（新提交 4 / 复用 1 / 唯一任务 5） | — |
| 2026-09-28 | 参考图①：dashscope | ✅ 身份/构图/绿蝶/金虫一致 | 3.00 |
| 2026-09-29 | 首尾帧②：dashscope + minimax | ✅ 且"收束"成立 | 5.00 |

**授权上限 60 元 / 单批 ≤ 20 元**，判定"上限即授权"：跑前把清单写进文档，跑完报账。

## 5. 迭代方法（工作流本身）

### 5.1 每次开发的固定八步（写在路线图 §5）

1. 读路线图、当前 Git 状态与相关模块；
2. 明确本次**只解决一个阶段的一个可验收切片**；
3. **先写/更新无费用测试，再实现**；
4. 跑编译、迁移、接口与前端交互验证；
5. 涉及付费：先说明 Provider/模型/参数/次数/预期成本/目的，等确认；
6. 存脱敏报告、任务 ID、结果路径与回归结论；
7. 更新路线图、测试记录与 Git 提交；
8. **只在工作区干净、验证通过后推送**。

### 5.2 排错纪律（比方法更重要）

- **失败信息常藏在进程内** → 旁路取证（读日志/探针），别靠反复重跑。
- **前端文案不是判据**（"服务未连接" ≠ 服务不可用）→ **先逐项读后端状态码**。
- **单轮红 ≠ 偶发，也 ≠ 回归** → 定性三件套：查历史判定 → 读失败轮请求序列 → **隔离复跑**。
- **改共用代码必须在新 HEAD 复跑**；推算值不得当基线引用。
- **修完要做证伪检验**，并核对还原指纹。
- **一个坏格子不该打穿整页**：容错要成对 —— **容错 + 留痕 + 修数据 + 堵源头**。

### 5.3 记忆与技能沉淀

- 三层记忆：`MEMORY.md`（只留约束与陷阱）、`PITFALLS.md`（判例）、`YYYY-MM-DD.md`（日志，只追加）。
- 可复用的工作流沉淀为 skill（用户级共 **15 个**，跨项目可用）。本项目直接产出与迭代的包括 `read-path-tolerance-hardening`（本次"坏单元格打穿整页"）、`local-app-zero-cost-regression`（零费用回归驱动）、`git-object-store-loss-recovery`（对象库损坏恢复）、`mermaid-diagram-set-render-verified`、`api-credential-vs-account-triage`（含 ark 退役沉淀的"开通有商业门槛"一节）。
- **口径变了要全量修正**，不只改眼前一处——避免文档之间漂移。

### 5.4 人机分工

**只有竹木能做的**：给钱与授权、查/充余额、定最终审美与范围、部署与对外发布、改 `.env`/密钥。
**其余由我自动接管**：写代码、写测试、跑回归、排错、落档、提交、录制无人演示。

### 6.1 剩余待办（按当前优先级）

| 4 | 索引增量重建（当前按项目全量重建） | 性能优化 | 我 | 0 |
| 5 | `ARK_IMAGE_MODEL` 换档（`doubao-seedream-5-0-260128` 已是 `Retiring`） | 定时炸弹，不在关键路径 | 我 | 0 |

理由一致 —— 都不影响"演出一支成片"，但每项都能吃掉一整天。

### 6.2 技术债（已知、已记录、未展开）

- 能力矩阵的时长/比例/分辨率**仍主要在 Provider 级**，未细化到模型级（P2 起就挂在账上）。
- 关键帧「重绘」仍走既有立即写版本的兼容接口，检查器中的选帧默认写入草稿（P3 技术债）。
- 检索仍是**字面召回**（FTS5 trigram + 本地 hash 向量），**不许讲成已有 RAG**。
- P5-B-1 的"按章圈范围"是**结构性范围收缩**（靠偏移裁剪），**不是语义检索**。

### 6.3 边界与红线（不许越过的）

- **审核门是真实关卡**，不许为了"顺滑"降级成提示。
- **状态色语义是产品语言**（蓝绿=进行中 / 琥珀=待审核 / 红=失败 / 紫=已修改），不许为"好看"改。
- **裸 SQL 写 JSON 列必然绕过序列化器** —— 凡直写 JSON 列的脚本都要复核。
- **未验的格子不许外推**：不得由 dashscope/minimax 的运行结果外推 ark 也能跑。
- 付费、删除、部署、改密钥 —— **必须先说清再动手**。

## 7. 一页速查

```
产品：文本 → 30~60s 短片，关键节点人工把关，全程可回退可追溯
技术：FastAPI + SQLite + LangGraph + 原生 JS + FFmpeg
规模：后端 15.4k 行 / 97 提交（2026-06-19 → 10-01）/ 18 份文档
验证：61 项零费用回归 · 581 断言 · 逐项零漂移 · 证伪检验 · 近两批真钱验收 8.00 元
默认：视频走 dashscope（wan2.7 三模式），ark 已退役
待办：部署（唯一硬缺口）> P1 微交互 > 语义 embedding
纪律：先写测试再实现 · 判据要能证伪 · 单轮红不等于回归 · 口径变了就全量改
```
